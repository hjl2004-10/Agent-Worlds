# 地图系统升级 · 现状研究笔记（v1）

> 用途：作为地图系统数字化升级多轮讨论的事实基础。
> 本文档只记录**现状是什么**和**问题在哪**，不做方案决定。
> 范围：A:\夸父（=GitHub main 65b638f，与生产一致）。

---

## 1. 系统全貌（数据流）

```
创作侧（目前只有 AI 产包）
  素材规范文档 ──► AI/手工 ──► .hjlmap 包
                                    │ POST /api/world/import（校验+落盘）
                                    ▼
存储层  data/worlds/<世界>/         static/public/{tiles,house,obstacles,sprites}/
        world.hjl                   （全局素材池，按文件名引用）
        scenes/<场景>/
          scene.hjl  tiles.hjl
          locations.hjl  obstacles.hjl
                │ 启动/切换时加载                │ 文件名引用
                ▼                               ▼
后端  env/map.py（常量+加载+查询）    FastAPI 静态托管
        ├─ map_l1/l2（碰撞/绕行数学）
        ├─ drive（三态漫游+to_target+god）
        └─ api: /locations /obstacles /tiles /world(s)/*/(switch) /world/export|import
                │ 500ms 轮询 JSON
                ▼
前端  MapView.tsx（1673行单文件）
        离屏整图+预放大缓存+量化相机 → Y-sort 场景物件 → NPC/覆盖层 → 小地图(独立DOM)
```

**NPC 侧对地图的全部感知**：`goto_location(地点名)`、`arrived_at` 两个工具 + 到达地点触发对话。NPC 不知道地图长什么样、不知道地形、不知道其他场景。

## 2. 数据 Schema 逐项盘点

### world.hjl
`world_id / display_name / genre / description / time / settings.day_ticks / lore{...} / assets.sprite_pool / available_scenes / default_scene`
- `sprite_pool` 引用的精灵不存在时**无人校验、静默失效**（现代都市的 pool 引用 `Adam_48x48`，实际文件是 `Adam_16x16`）

### scene.hjl
`scene_id / display_name / description / map{width,height,tile_size} / spawn_points / exits`
- **`map` 字段是摆设**：后端从不读取，真实尺寸来自 `env/map.py` 硬编码常量
- **`exits` 字段从未被任何代码消费**（全仓库 0 引用）——多场景连通从未实现
- `spawn_points` 支持 per-NPC 出生点（按 NPC 名），实际只用了 `default`

### tiles.hjl
`tiles: [[瓦片文件名, ...], ...]`
- 纯视觉引用，**没有任何语义**：无地形类型、无可通行性、无速度修正、无音效/事件钩子
- 理论上支持任意尺寸（前端离屏画布按 `tiles.length` 动态构建），但后端常量钉死 320

### locations.hjl
`{地点名: {x,y, tile[格坐标], building, desc, greeting}}`
- 地点 = 一个点 + 一句话 + 一张建筑图。**没有区域/房间概念**，没有进入/离开事件（只有到达触发）
- `building` 路径风格 `house/xxx.png`（相对），与 obstacles 的 `/obstacles/xxx.gif`（绝对）**不统一**

### obstacles.hjl
`[{id, type: rect|circle, x, y, width/height | radius, desc, sprite}]`
- `sprite` 的视觉锚点=碰撞盒左上角、尺寸固定 48 地图像素——**视觉与碰撞盒解耦不了**（campus 的喷泉碰撞盒在视觉下方，我们只能取折衷）
- 只有 rect/circle 两种碰撞原语

### NPC 位置
`data/individuals/*.hjl → position: {"<world>:<scene>": {x,y}}` —— 多场景坐标键**格式已就绪**，缺的是场景间的移动机制

### 素材池
`static/public/` 四个子目录全局共享，**按文件名引用 = 同名覆盖**；无元数据（尺寸/作者/标签/来源），无删除追踪（删素材会静默破坏引用它的地图）
- 渲染尺寸全部写死在代码里：精灵 16×24 地图像素、建筑 32、障碍物 48、状态图标 24、名牌字号 3×renderScale

## 3. 后端逻辑现状

| 模块 | 现状 | 局限 |
|---|---|---|
| 常量 (`env/map.py`) | TILE_SIZE=16, MAP 320×320, CONTACT 12 / LEAVE 24, GOD_MOVE_SPEED=60 | **9 个文件引用常量**；scene.hjl 里的 map 字段不生效 |
| 碰撞 (`map_l2`) | 点∈矩形/圆 + 线段-矩形相交（视线检测） | 点检测意味着 NPC 可能穿角；无碰撞图层（tile 不参与碰撞） |
| 移动 (`drive_l2.move_toward_target`) | 直线步进 + 被挡时「找阻挡物→算绕行向→试反向→试垂直」 | **不是寻路**：L 形凹槽/复杂建筑群会卡死或原地踏步；无路径成本概念 |
| 漫游 (`drive_l1`) | idle→random→linear 三态循环，时长 per-NPC 可配 | 随机步进同样只做单点碰撞检查 |
| 地点到达 | to_target 到达→`_trigger_location_encounter` 触发对话 | 无"进入区域"持续状态 |
| 世界/场景切换 (`api/world.py`) | 保存 NPC→重置→加载→前端整页 reload | 切场景必须刷新页面；无跨场景移动 |
| 导入导出 (`api/map_io.py`) | .hjlmap 1.0：结构校验+引用完整性+尺寸规范（软警告/硬拒绝）+素材打包 | 无 schema 版本号迁移机制；导出以"当前素材池"为准，无独立素材库概念 |

## 4. 前端渲染现状（MapView.tsx 单文件 1673 行）

已经相当强：离屏整图 + renderScale 预放大缓存 + 相机量化（像素稳定零闪烁）、cover 倍率缩放（无黑边）、拖拽/触控板节流、Y-sort 场景物件（GIF 静帧入 canvas 参与遮挡）、覆盖层 DOM 直改（60fps 不 setState）、独立小地图。

**结构性问题**：
1. **单文件巨石**：渲染、相机、交互、覆盖层、小地图、数据加载全在一个组件里，没有图层抽象——加任何新图层类型都要改这个文件
2. MAP_WIDTH/HEIGHT 仍是文件级常量（/api/status 里有 map_width 但前端不读）
3. 每帧全量重绘所有实体（当前规模 OK，实体多了需要脏矩形/分层 canvas）
4. 地图数据加载与渲染耦合（fetch 散落在 useEffect 里，没有地图数据 store）
5. 场景切换 = `window.location.reload()`

## 5. 现存数据质量实况（手写数据不可靠的证据）

| 场景 | 瓦片网格 | 问题 |
|---|---|---|
| modern/office | 20×20 | 标准 |
| campus/campus | 20×20 | 标准（AI 产包导入） |
| apocalypse/camp | **16 行 × 20 列** | 不是矩形规格，地图"缺了一角"且无人发现 |
| default/town | **19 行 × 20 列** | 同上 |
| comic/studio | **0×0（空）** | 一直渲染降级深色地面 |

——地图数据从来没有被校验过"规格一致性"，前端只是静默容错。这直接论证了升级必须有 schema 校验 + 编辑工具。

## 6. 硬编码/耦合清单（任何升级方案的"必答题"）

1. 地图尺寸 320×320×16 双端硬编码，scene.hjl 字段空转
2. 碰撞原语仅 rect/circle，且 sprite 视觉与碰撞盒锚点绑定
3. 无寻路（单步避障 ≠ 路径规划）
4. exits/spawn 的多场景机制只有数据格式，没有行为
5. 素材全局池按文件名引用：同名覆盖、删除无追踪、无元数据
6. tiles 无语义层（地形/通行/事件）
7. .hjlmap 无版本化 schema
8. 创作链路 = 「给 AI 发规范文档 → AI 产包 → 导入」这一条独木桥，无人工编辑入口
9. 地点无区域概念；无进入/离开/停留事件
10. NPC 对空间无感知（只有地点名工具）

## 7. 升级讨论议题清单（后续逐轮拍板，每轮一个）

- **R1 数字化的定义与边界**：地图"一等公民"指什么——ID/版本/校验/查询/变更流？
- **R2 数据模型 2.0**：地形语义层怎么加（tile 级 vs 覆盖层级）？任意尺寸怎么落地？schema 版本迁移？
- **R3 素材库**：SQLite（已有 db 双写层可复用）vs 文件+manifest？元数据、去重、权限？
- **R4 编辑器形态**：Web 内嵌（上帝模式扩展出"建造模式"？）vs 独立编辑页 vs 离线工具？实时预览怎么和现有渲染复用？
- **R5 创作者工作流**：从素材→地图→场景逻辑→发布的完整链路分几步？每步什么工具？AI 协作点放哪（自然语言造图？）？
- **R6 运行时升级**：寻路（格 A* vs navmesh）、多场景连通（exits 传送 vs 大地图流式）、相机分区
- **R7 兼容与迁移**：现有 4 世界 5 场景无损迁移方案（i18n 事故的教训：绝不做破坏性覆盖）
- **R8 NPC 空间感知**：AI 创作者（NPC 造地图？）与空间工具组（whereami/look/path）

## 8. 本次研究结论（供讨论起点，非决定）

1. **地基比预想的好**：.hjlmap 管线（校验+素材打包）、离线渲染优化、多场景坐标键、spawn/exits 数据格式都已存在——升级不是从零开始，是"把占位格式变成真机制 + 补创作工具"
2. **最大的洞是"没有编辑器 + 没有语义层"**：所有地图内容都靠 AI 一次性产包，人类无法微调（改一个瓦片要手写 JSON）
3. **所有升级必须先过"数据迁移"关**：现有数据已经不一致（16 行/19 行/空网格），2.0 schema 要带迁移器 + 校验器
4. MapView 需要先做**图层化重构**才能承载编辑器（编辑器需要：瓦片笔刷层、碰撞可视化层、实体拖放层、网格吸附——全部要求图层抽象）
